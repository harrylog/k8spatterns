● The editor kubectl edit opens is vim. These are the quickest ways to find the
  right spot.

  1. Know where it goes

  volumeMounts belongs inside the app container, at the same indentation as
  image:, command: and resources::

  spec:                      # Deployment spec
    template:
      spec:                  # Pod spec
        containers:
        - name: app          # <- your container
          image: ...
          command: ...
          volumeMounts:      # <- here, same column as image:/resources:
          - name: logs
            mountPath: /var/log

  If you're not sure of a path, kubectl explain tells you where a field lives:

  kubectl explain deploy.spec.template.spec.containers.volumeMounts

  2. Jump there in vim

  kubectl edit lists fields alphabetically, so inside the container the last
  field is terminationMessagePolicy. Anything starting with "v" goes after it.

  - Type /terminationMessagePolicy and press Enter. The cursor jumps to that
    line. Press n if it lands somewhere else.
  - Press o to open a new line below. Vim keeps the current indentation, so
    you're already in the right column.

  To check that you're in the right column, run :set number cursorcolumn. It
  shows line numbers and a vertical line at the cursor, so you can see that
  volumeMounts lines up with image: above it.

  3. Paste without broken indentation

  Pasting into vim often makes the indentation cascade to the right. To avoid
  that:

  :set paste      # then press i and paste
  :set nopaste    # afterwards

● I rewrote exam-practice/q01-sidecar-logging/solution.md to answer all three
  questions. I validated the full Deployment YAML against the cluster with a dry
  run, and the tail -f/tail -F behavior it describes was tested in a Pod here.

  The issue. kubectl logs only shows what a container writes to stdout/stderr.
  The legacy app writes to /var/log/legacy-app.log instead. That file is inside
  the app container's own private filesystem, so no other container can see it,
  and it's lost if the container restarts. You also can't change the app, so you
  have to work around it.

  Why a sidecar. Containers in the same Pod always run on the same node and can
  share volumes. A second container can read the app's file and print it to its
  own stdout without touching the app. Once it's on stdout, kubectl logs -c 
  sidecar (and any log collector) can see it.

  Why emptyDir. It's a directory shared by every container in the Pod, created
  when the Pod starts and deleted with it. That matches the need exactly, with
  no setup. The other volume types are worse here:
  - medium: Memory: RAM-backed, and it counts against the Pod's memory limit.
  - hostPath: ties the Pod to one node's directory, and replicas on the same
    node write to the same file.
  - PVC: overkill for temporary logs, and it breaks with several replicas on
    different nodes.
  - ConfigMap or Secret: mounted read-only, so the app can't write.

  Other ways to solve it:
  - Native sidecar (initContainers with restartPolicy: Always). It fails with
    the exact command the task gives: it starts before the app, the log file
    doesn't exist yet, and tail -f exits with code 1. Using tail -F makes it
    work, because -F waits for the file to appear.
  - Make the app log to stdout, for example with ln -sf /dev/stdout on the log
    file. It's the best fix in real life, but the task forbids changing the app
    container.
  - A log-shipper sidecar (Fluent Bit and similar) sends the file straight to a
    logging backend. kubectl logs still won't show anything, so it doesn't meet
    the task.
  - A node-level log agent (DaemonSet) only reads stdout/stderr, so it can't see
    the file. You'd still need a sidecar alongside it.
  - kubectl exec ... tail is fine for a quick look while debugging, but it
    changes nothing.

  The file also has the complete final YAML, without the [...unchanged...]
  shorthand that caused your error. It shows where each of the three new blocks
  goes and how to check the edit really landed (a new Pod showing 2/2, not just
  rollout status). It ends with a list of common mistakes, including the three
  in your q1.yaml.
